# TIK TAK — project structure & conventions

## Folder layout
- `src/app` — routing only. Each `page.tsx` is a thin wrapper: imports a view from `@/views`, adds `metadata`/`generateMetadata`, and wraps with `RequireAuth`/`RedirectIfAuth` if needed (unless a parent `layout.tsx` already does it for the whole subtree — see Categories/Account/Favorites sections below). No business logic here.
- `src/views` — the real per-route UI + data fetching. One file per route, barrel-exported via `src/views/index.ts`. Data fetching is a mix of two patterns depending on age/whether the data is shared across components — see "Data fetching & mutations" below; prefer the `useQuery`/`useMutation` hook pattern for anything new.
- `src/shared/components` — reusable UI (`ui/`, `layout/`, `landing/`, `auth/`, plus top-level like `ProductCard.tsx`, `CategoryCard.tsx`, `CategoryProductCard.tsx`, `ProductDetailContent.tsx`). Barrel: `src/shared/components/index.ts`.
- `src/shared/hooks` — one file per data domain, each exporting a `useX` query hook (+ `xQueryKey` constant) and, where mutations exist, a `useXMutations`/`useUpdateX` hook: `useBasket.ts`, `useFavorites.ts`, `useProfile.ts`, `useProducts.ts`, `useOrders.ts` (also exports `useOrder(id)`). Plus non-data hooks like `useCardCarousel`, `useHasMounted`, `useIsomorphicLayoutEffect` (see "Data fetching & mutations" for the latter two).
- `src/shared/utils` — plain helper functions, no React: `pagination.ts` (`paginate`, `getTotalPages` — used by every paginated list), `orderStatus.ts` (`ORDER_STATUS_LABELS`/`ORDER_STATUS_COLORS` maps), `seo.ts` (`buildMetadata`, `SITE_URL`, `SITE_NAME` — see "SEO" section).
- `src/shared/constants` — `images.ts` exports `PRODUCT_IMAGE_FALLBACK`, a static placeholder image URL used everywhere a product's `img_url` may be `null`/empty (`src={product.img_url || PRODUCT_IMAGE_FALLBACK}`). Its host is in `next.config.ts` `remotePatterns` even though these components use plain `<img>`, not `next/image` — kept there for consistency/documentation, not because it's required for `<img>`.
- `src/assets` — static assets meant to be ES-imported (not served raw from `/public`): `src/assets/images/` (e.g. `category.png`, `tiktak-login.webp` — the strawberry/milk banner graphic reused across auth + categories), `src/assets/fonts/`, `src/assets/web-icon/`. Import directly (`import x from '@/assets/images/foo.png'`) and render via plain `<img src={x.src}>` for API-driven surfaces — but for these two specific static banners rendered via `next/image` (`CategoriesPage`, `CategoryDetailLayout`), pass the imported object directly as `src` (not `.src`) so Next can derive intrinsic dimensions.
- `src/services` — one file per API domain (`product.service.ts`, `order.service.ts`, etc.), all going through `src/services/httpClient.ts` (axios wrapper with token refresh interceptor, browser-only — reads/writes the *visitor's* token via `localStorage`). `src/services/Auth/auth.service.ts` lives in a subfolder. `src/services/serviceAccount.ts` is a separate, **server-only** client (`import 'server-only'`) used exclusively for SSR-ing public catalog data — see "SSR & the service account" section; never import it from a Client Component.
- `src/types` — **the only place `interface`/`type`/enum-const declarations may live.** Organized by domain folder (`user/`, `product/`, `campaign/`, `order/`, `basket/`, `category/`, `favorites/`, `account/`, `auth/`, `upload/`, `shared/`, `common/`). One declaration per file, filename === export name (e.g. `types/product/Product.ts`, `types/product/ProductCardProps.ts`). Each domain folder has its own `index.ts` barrel; component `*Props` types live here too (not inline in the component file). Cross-domain imports go through the sibling domain's barrel (`from '../category'`); same-domain imports are direct (`from './OrderStatus'`). Top-level `src/types/index.ts` re-exports everything.

## Backend / API
- Real backend: `https://api.sarkhanrahimli.dev/api/tiktak` (documented in `web.md` at repo root — client/web scope only; there's a separate admin API not covered here).
- Base URL comes from `NEXT_PUBLIC_API_BASE_URL` in `.env.local` (not committed — recreate it if missing: `NEXT_PUBLIC_API_BASE_URL=https://api.sarkhanrahimli.dev/api/tiktak`). Without it, every request silently fails and pages render empty.
- Auth is bearer-token based, tokens stored in `localStorage` (`access_token`/`refresh_token`, managed in `httpClient.ts`). `RequireAuth`/`RedirectIfAuth` (in `src/shared/components/auth/`) check `localStorage` client-side only — they don't validate the token server-side.
- **Most endpoints require auth** (`/products`, `/products/:id`, `/categories`, `/basket`, `/orders/*`, `/profile`) — confirmed via direct testing, not just docs. Only `/campaigns` is public. Any route whose UI is fetched with the *visitor's* token (via `httpClient.ts`) must be wrapped in `RequireAuth` — either directly in `page.tsx` (see `basket/page.tsx`, `account/layout.tsx`, `favorites/page.tsx`) or once in a parent `layout.tsx` covering the whole subtree — or it'll silently show empty data instead of a real error.
- **Exception:** `/categories`, `/categories/[id]`, `/products`, `/products/[id]`, `/categories/[id]/products/[productId]` are **not** wrapped in `RequireAuth` — anonymous visitors can browse the full catalog. This works despite the backend requiring auth because these routes fetch data server-side through the **service account** (see "SSR & the service account"), not through the visitor's own token. Personalized bits on these same pages (basket quantity, favorite heart state) still come from the visitor's own `useBasket()`/`useFavorites()` and are simply empty/unfilled for anonymous visitors. Clicking "Səbətə əlavə et" or the heart icon while anonymous doesn't silently fail — `useBasketMutations`/`useToggleFavorite` check `getAccessToken()` first and `router.push('/login')` instead of firing the request if there's no token (see "Data fetching & mutations").
- `next.config.ts` `images.remotePatterns` must list every real image host the API returns (currently `picsum.photos`, `uploads.sarkhanrahimli.dev`, `www.tiktak.az`) or `next/image` throws at render time and the whole subtree fails silently. Because category/product image hosts are attacker-uncontrolled but still *unpredictable* (API-driven, not guaranteed to match the allowlist), `CategoryCard` and `CategoryProductCard` deliberately use a plain `<img>` (not `next/image`) for API-provided images — an unlisted host just fails to load the image instead of crashing the page. Prefer this pattern for any new component rendering API-supplied image URLs.
- Some `web.md`-documented query params are marked "(disabled)" — take that literally, not as "optional." E.g. `GET /products?category_id=` returns a 400 on the real backend despite being documented. Filter client-side on `product.category.id` instead of trusting the query param.
- **`web.md` is unreliable about response envelopes — verify empirically, don't trust the doc's example JSON.** Most endpoints wrap the payload in `{message, data, result}` (products, categories, basket, favorites, profile, `POST /orders/checkout`, `GET /orders/user`) — but `GET /orders/user/:id` returns the **raw** `Order` object directly, no envelope, even though `web.md` shows it wrapped the same as the list endpoint. Confirmed by hitting the live API directly with `curl`/`fetch` (not by reading docs or guessing from a runtime error alone — do this for any new order/profile-adjacent endpoint before wiring it up). `order.service.ts`'s `getById` is typed `Order` (unwrapped); `checkout`/`list` are typed `ApiResponse<Order>`/`ApiResponse<Order[]>`. Getting this wrong doesn't throw a type error (axios/TS can't catch it) — it just silently renders nothing or crashes with e.g. `orders.map is not a function`.
- `User` (`GET /profile`) actually has an `email: string | null` field returned by the live API — `web.md`'s example JSON omits it entirely. There's no way to set it (not in `UpdateProfilePayload`, not in the signup payload) — it's shown read-only in `AccountPage`. If `web.md` doesn't mention a field, that means "not documented," not "doesn't exist" — worth an empirical check before assuming.
- There is a reference admin panel at `https://github.com/Xeyyam456/TikTak-Project-Admin-Panel` (Vite/React) — same backend, useful to cross-check endpoint paths/response shapes and its `src/types` folder structure (which this project's `src/types` convention was modeled after, minus its `*Api`-vs-UI-model split since this app renders the API shape directly).

## SSR & the service account
- The backend has no public/guest read endpoint for `/categories` or `/products` (confirmed empirically), and the app's auth is `localStorage`-only (unreadable during server rendering) — so real SSR of catalog data would be impossible without a workaround. The workaround: `src/services/serviceAccount.ts` authenticates as **one dedicated, non-real-user account** (credentials in `SERVICE_ACCOUNT_PHONE`/`SERVICE_ACCOUNT_PASSWORD`, server-only env vars, **not** `NEXT_PUBLIC_`, so they never reach the browser bundle) and caches its own access/refresh tokens in module-scope memory, independent of whoever is viewing the page.
- `serviceGet<T>(path)` is the only export components should call. It transparently refreshes the cached token when it's near expiry, and if the refresh token has *also* expired, falls back to a full re-login with the stored credentials — fully self-healing, no manual intervention needed after deploy.
- Used by: `HomePage.tsx` (campaigns — actually public, but same helper isn't needed there, it uses `campaignService` directly), `CategoriesPage.tsx`, `ProductsPage.tsx`, `src/app/categories/layout.tsx` (categories list, passed down as a `categories` prop to `CategoryDetailLayout`), `src/app/categories/[id]/page.tsx` (products, filtered by category and passed as a `products` prop to `CategoryProductsSection`), and both product-detail `page.tsx`/`generateMetadata` pairs (`products/[id]`, `categories/[id]/products/[productId]` — fetch the product once server-side, pass as `initialProduct`).
- **This data is identical for every visitor** (it's the service account's view, not the real visitor's) — fine for catalog listings/product info, but never use `serviceGet` for anything personalized (basket, favorites, orders, profile). Those stay exactly as before: client-fetched with the visitor's own token via the normal `useX()` hooks.
- `revalidate = 300` (ISR) is set on every route that uses `serviceGet`, so the catalog re-fetches at most every 5 minutes rather than on every request.

## SEO
- `src/shared/utils/seo.ts` exports `buildMetadata({ title, description, path, robots? })` — the standard way to build a `Metadata`/`generateMetadata` return value. It fills `alternates.canonical`, mirrors title/description into `openGraph`/`twitter` (Next doesn't do this automatically), and defaults `robots` to `{ index: false, follow: false }` — a page must opt **into** indexing, not out of it. Every `page.tsx`'s `metadata`/`generateMetadata` should go through this rather than a bare object literal.
- Only `/` (`src/app/page.tsx`) passes `robots: { index: true, follow: true }` — it's the only page with real SSR content a crawler could usefully index (see "SSR & the service account" — the catalog pages *are* server-rendered now, but the plan never revisited their `robots` default; they still default to `noindex` via `buildMetadata`, which is intentional since their content is identical for every visitor/service-account view and not meaningfully unique per URL from an SEO standpoint... re-check with the user before changing this).
- `src/app/robots.ts` / `src/app/sitemap.ts` — generated via `MetadataRoute.Robots`/`MetadataRoute.Sitemap`. The sitemap deliberately lists only `/` (the only genuinely public, non-auth-walled, indexable route) — don't inflate it with auth-walled URLs. `sitemap.ts`'s `lastModified` is computed **once at module load** (`BUILD_TIME` constant), not via `new Date()` per-request, so it doesn't dishonestly claim "modified now" on every crawl.
- `src/app/opengraph-image.tsx`, `twitter-image.tsx`, `icon.tsx`, `apple-icon.tsx` — generated at request time via `next/og`'s `ImageResponse` (brand green `#114F2E` background, system sans-serif, no external font fetch) since there's no logo/brand image asset anywhere in the repo. Don't source a static image for these without checking whether a real logo has since been added.
- `/` (`HomePage.tsx`) is the one page genuinely SSR'd for SEO purposes — it's an `async function` Server Component that `await`s `campaignService.list()` directly (no `'use client'`, no `useEffect`), because `/campaigns` is the only endpoint that's actually public. It also renders a `<script type="application/ld+json">` (Organization + WebSite schema) inline.
- Auth-gated detail pages (`ProductDetailContent.tsx`, `OrderDetailSection.tsx`) can't get a real server-rendered `<title>` for personalized routes (the same `localStorage`-only-auth problem), so they sync `document.title` client-side in a `useEffect` once their data loads, as a best-effort fix for the browser tab title — this is a deliberate workaround, not a sign that `generateMetadata` is broken there.

## Layout / chrome rules
- `SiteChrome.tsx` controls Header/Footer per route: `/login` and `/register` render with **no chrome** at all; **Footer only renders on `/` (landing)** — every other route gets Header but no Footer.
- `SiteChrome.tsx`'s `<main>` has `bg-neutral-50` (not white) for every non-login/register route — this is intentional site-wide now, not a one-off for categories.
- Header shows a centered search input on every route except `/`; on `/` it's just the logo + nav. Search filters `useProducts()` client-side by `title` only (not description — deliberately narrowed), results in a dropdown, click navigates to `/products/:id` and clears the query. Query resets on every route change (Header is persistent across navigations, so its local `query` state doesn't auto-clear on its own — there's a render-time "adjust state when a prop/pathname changes" block for this, not a `useEffect`, to dodge the `react-hooks/set-state-in-effect` lint rule; see "Data fetching & mutations" for why that pattern over a plain effect).
- The address block and the "Hesabım" avatar (`Header.tsx`, next to the logo / in the account nav link) both come from `useProfile()` (see below) — shows `profile.address` / `profile.img_url`, falling back to "Ünvanınızı seçin" / a generic user icon if absent. Because `useProfile()` is a shared TanStack Query cache, saving a new address or avatar in `AccountPage` updates the Header immediately with no extra plumbing.
- Header's top row has an explicit `h-10` wrapper around its flex children (separate from the padded `Container`, since combining a fixed height with padding on the same element fights `box-sizing: border-box`). This exists so the logo sits at an identical pixel Y position on every route — without it, the address block (icon + two text lines, ~46px tall) is taller than the logo (~40px) and `items-center` pushes the logo down by a few px only on non-landing pages. Don't remove this wrapper without re-checking that cross-page consistency.
- Header shows a **"Çıxış" (logout) button** in the nav, only when `hasMounted && profile` (see "Data fetching & mutations" for why `hasMounted`) — i.e. only for a confirmed-logged-in visitor, never during SSR/anonymous browsing. Clicking it opens the shared `ConfirmModal` ("Hesabdan çıxmaq istəyirsiniz?"); only on confirm does it `clearTokens()` + `queryClient.clear()` (wipes cached profile/basket/favorites so nothing stale flashes) + a `sonner` success toast + `router.push('/')`. `AuthPage.tsx`'s login handler fires its own success toast right before redirecting to `/`. Neither of these toasts lives in a TanStack mutation hook (login/logout aren't `useMutation`-based) — that's a deliberate, narrow exception to the "toasts live in the mutation hook" rule below, since there's no hook here to put them in.
- Brand color is `--primary: #114F2E` (green), defined in `globals.css` and used via `text-primary`/`bg-primary`/`border-primary` Tailwind classes — don't hardcode the hex elsewhere, use the token. Note several newer category-page elements use one-off hex greens (`#92D871`, `#0A955E`, `#76CB4F`) that are visually related but distinct tokens, not `--primary` — matched to existing AuthPage/banner colors, not something to "fix" to `--primary`.
- **Most interactive buttons use `rounded-[8px]`** (heart, +/− steppers, form submit buttons, etc.) — this does **not** apply to purely decorative circles (avatars, loader dots, count badges, radio-select indicators) or to card containers (`rounded-2xl`). **Exception:** the landing page's carousel prev/next arrow buttons (`BannerCarousel.tsx`, `SpecialOffers.tsx`) are deliberately `rounded-full` circles, reverted back from an earlier project-wide `rounded-[8px]` pass — don't "fix" them back to `rounded-[8px]`. When adding a new button, default to `rounded-[8px]` unless it's one of these two carousel arrows.
- Global scrollbar is hidden everywhere (`globals.css`) but scrolling still works; this was intentional, not a bug.
- Fonts (`src/app/layout.tsx`): `Roboto` (site-wide default, via `--font-roboto` → `--font-sans`) **must** load with `subsets: ["latin", "latin-ext"]`, not just `["latin"]` — Azerbaijani letters (ə, ş, ç, ğ, ö, ü) live in `latin-ext` and silently fall back to a different system font otherwise. `Poppins` (`--font-poppins`) is also loaded, used only for display text inside the green promo banners (via inline `style={{ fontFamily: 'var(--font-poppins)' }}`) as a free stand-in for the (unlicensed, can't be downloaded) "Codec Pro" font from the original design mockups.

## Categories feature (`/categories`, `/categories/[id]`)
- `/categories` (`CategoriesPage`) is the grid overview: a green promo banner (reusing `src/assets/images/tiktak-login.webp`) plus a `CategoryCard` grid. It's an `async function` Server Component now (no `'use client'`) — fetches via `serviceGet` (see "SSR & the service account"), not `categoryService.list()` client-side.
- `/categories/[id]` is a product listing for one category. It's split across a **persistent layout + swappable page** on purpose:
  - `src/app/categories/layout.tsx` — an `async function` Server Component (no `RequireAuth` — see "Backend / API" exception) that fetches the categories list via `serviceGet` and passes it as a `categories` prop into `src/views/CategoryDetailLayout.tsx`, which renders the left sidebar (category list + `category.png` promo banner) and the right "Səbətim" (basket) panel. `CategoryDetailLayout` itself is still `'use client'` (needs `usePathname`/`useParams`) but no longer fetches anything itself. Branches on `usePathname() === '/categories'` to render bare `{children}` (no shell) for the index route.
  - `src/app/categories/[id]/page.tsx` — also `async`, fetches products via `serviceGet` and filters client-side (in the Server Component, before sending to the browser) by `product.category.id`, passing the filtered array as a `products` prop into `src/views/CategoryProductsSection.tsx` (which is now a plain presentational Client Component — no fetch, no `categoryId` prop, just renders what it's given).
  - **Critical gotcha:** the shared layout must live at `src/app/categories/layout.tsx`, **not** `src/app/categories/[id]/layout.tsx`. A layout placed inside the `[id]` folder still gets remounted by Next.js every time the `id` param changes (verified empirically with Playwright — DOM identity lost, effects re-ran), defeating the point of a persistent shell. Read the dynamic id client-side via `useParams()` in the persistent component instead of via server `params`.
  - **Sidebar/basket/grid height matching is pure CSS now — no JS measurement.** The three-column row (`<div className="flex items-stretch gap-4">` in `CategoryDetailLayout.tsx`) uses `items-stretch`; the sidebar (category list + banner) is the **only** column that contributes real content height. The middle column and `BasketSidebarPanel` are `relative` wrappers whose actual content is `absolute inset-0` — meaning they can never inflate (or shrink) the row's height, they simply stretch to match whatever the sidebar naturally is. This replaced an earlier `ResizeObserver`/`requestAnimationFrame`-based JS measurement approach (`useCategorySidebarHeight` context, now **deleted** — don't try to re-add it or import it, it no longer exists) that caused a visible first-paint jump on SSR'd cold loads (JS hydration and the service-account round-trip both take real time; the JS-measured height wasn't ready yet, so the panel briefly rendered at its own unconstrained size before snapping to the right height once JS caught up — confirmed and fixed after extensive Playwright-based root-causing). Pure CSS has zero dependency on hydration timing, so this can't recur. **Do not reintroduce a JS-measured height for this layout** — if a future change seems to need one, that's a sign the CSS-stretch structure got broken, not that JS measurement should come back.
  - `BasketSidebarPanel` (`src/shared/components/BasketSidebarPanel.tsx`) has two sizing modes via its props: `fill` (boolean) — used only by `CategoryDetailLayout`, renders its content as `absolute inset-0` per the point above — vs. `height` (number/string) — used by `FavoritesPage`, which gives it a real computed pixel height instead (`clampToViewport(BASKET_PANEL_HEIGHT - 14)`), since Favorites' layout isn't in a stretched flex row. Don't mix the two: `fill` and `height` are alternate modes, not composable.
  - `CategoryProductCard` (used on the category/favorites product grids, not `ProductCard`) renders a real image (`PRODUCT_IMAGE_FALLBACK` if missing), price, and an "Səbətə əlavə et" button that swaps to a `− <qty> +` stepper on click (optimistic UI via `useBasketMutations`, see below). Reverts to the plain button at quantity 0. The card itself has a **fixed `h-[244px]`** and the title is a **fixed `h-[48px]` + `line-clamp-2`** (with `min-h-0` on that wrapper — flex items ignore an explicit height without it, a classic flexbox gotcha) so every card in a grid is pixel-identical regardless of title length; don't remove the fixed sizing to "fit the content," it was added specifically because CSS Grid's default `align-items: stretch` made card height vary per-row based on neighboring titles. Clicking the card body navigates to a product detail view (see next section) — clicking the heart or +/− buttons calls `e.stopPropagation()` first so it doesn't also trigger navigation. `quantity`/`isFavorite` are gated behind `useHasMounted()` (see "Data fetching & mutations") since this card now renders on SSR'd pages.

## Product detail pages (`/products/:id`, `/categories/:id/products/:id`, `/favorites/:id`)
- All three routes render the **same** `ProductDetailContent` component (`src/shared/components/ProductDetailContent.tsx`) — back button, favorite toggle, image, title/description/price, and an add-to-basket control that shows a plain "Səbətə əlavə et" button when not in the basket, or a green "✓ Səbətdədir" pill + separate red trash button (opens `ConfirmModal`) when it is. It takes `productId`, `initialProduct` (optional, SSR'd data — see below), `height`, `className`, and an optional `onBack` (defaults to `router.back()`) so each route can size/position it differently:
  - `/products/[id]` (`ProductDetailPage`) — full page, own `Container`, no `height` prop (natural height). No `RequireAuth`.
  - `/categories/[id]/products/[productId]` (`CategoryProductDetailSection`) — rendered inside `CategoryDetailLayout`'s persistent shell with `height="100%"` (fills the CSS-stretched wrapper — see "Categories feature" for why there's no JS-measured height anymore). No `RequireAuth`.
  - `/favorites/[id]` — rendered *inline* inside `FavoritesPage` itself (not a separate view/layout split), still `RequireAuth`-gated — see Favorites section below for why.
- **`initialProduct`**: both non-favorites routes' `page.tsx`/`generateMetadata` fetch the product server-side via `serviceGet` (see "SSR & the service account") and pass it down as `initialProduct`. `ProductDetailContent` uses it as the initial `product` state and **skips its own client fetch** when present (`useEffect` early-returns if `initialProduct` was given). `/favorites/[id]` never passes `initialProduct`, so it falls back to the original client-side `productService.getById()` fetch — this dual-mode behavior is intentional, don't remove the fallback path.
- `quantity`/`isFavorite` (from the visitor's own `useBasket()`/`useFavorites()`) are gated behind `useHasMounted()` for the same hydration-safety reason as `CategoryProductCard` — see "Data fetching & mutations".
- Don't add a fourth "Səbətə əlavə et"/stepper variant elsewhere; if a new surface needs product-detail UI, reuse `ProductDetailContent`.

## Favorites feature (`/favorites`, `/favorites/:id`)
- `/favorites` (`FavoritesPage`) shows a paginated `CategoryProductCard` grid (5 cols × 2 rows = `PAGE_SIZE` 10, via `src/shared/utils/pagination.ts`) plus a `BasketSidebarPanel` on the right, mirroring the categories layout but **without** a separate persistent-layout file — it's all one component, because the "list vs. detail" swap here is local UI state, not routing (see next point).
- Clicking a card does **not** navigate away — `CategoryProductCard`'s `onSelect` prop is used to swap the grid for an inline `ProductDetailContent` while staying on `/favorites/:id` (so the basket panel on the right never unmounts). The current page number is carried in the URL as `?page=` (e.g. `router.push('/favorites/${id}?page=${currentPage}')`) specifically so that navigating into a detail view and back preserves which page you were on — `FavoritesPage` is the same component for both `/favorites` and `/favorites/[id]` (`src/app/favorites/[id]/page.tsx` renders it too), reading `useParams().id` and `useSearchParams().get('page')` itself rather than taking them as props.
- `CategoryProductCard`'s `onSelect` is otherwise unused (undefined) on `/categories/[id]`, where clicking instead does a real route navigation to the nested product route above — same card component, two different click behaviors depending on which page renders it.

## Account feature (`/account`, `/account/orders`, `/account/orders/:id`)
- Same **persistent layout + swappable page** shape as Categories: `src/app/account/layout.tsx` wraps `RequireAuth` + `AccountLayout` (sidebar nav: "Hesab məlumatlarım" → `/account`, "Sifarişlərim" → `/account/orders`, both `<Link>`s so the layout never remounts between them) around `{children}`; `AccountPage`/`OrdersPage`/`OrderDetailSection` are just the swappable middle content, no `Container`/card chrome of their own (the layout's card supplies it).
- Sidebar active-state matching isn't a plain `pathname === href`: `/account` needs an exact match (else it'd also light up on `/account/orders`), but `/account/orders` needs `pathname.startsWith(href)` so it stays highlighted on `/account/orders/:id` too. Same asymmetric pattern is used for the Header's "Hesabım" nav link (`pathname.startsWith('/account')`).
- `AccountPage` edits `full_name`/`address`/`password`/`password_repeat` via `useUpdateProfile()` (`PUT /profile`) — `phone` and `email` are shown but `disabled`/`readOnly`; there is no backend field/endpoint to change either (confirmed against `web.md` + the signup payload, not assumed).
- Avatar upload: picking a file shows an instant local preview (`URL.createObjectURL`), uploads via `uploadService.upload(file)` (`POST /upload` → `{ url }`), then **immediately** calls `useUpdateProfile()` with that `img_url` (auto-save, no separate "save" click needed) — and must also resend the current `full_name`/`address`, because `PUT /profile` is a real PUT: sending only `{ img_url }` either gets rejected or silently drops the other fields. This bit the avatar feature once already; don't send a partial payload to `profileService.update()`.
- `/account/orders` table columns map to real `Order` fields (`orderNumber`, `createdAt`, `address`, `items.reduce(quantity)`, `total`/`deliveryFee`, `status` via `ORDER_STATUS_LABELS`/`ORDER_STATUS_COLORS`) — paginated the same way as Favorites (`PAGE_SIZE = 7`). ## Data fetching & mutations
- **New/updated code should use the TanStack Query hook pattern**, not raw `useState`/`useEffect` + service call. Every domain hook in `src/shared/hooks` follows the same shape: export a `xQueryKey` array constant, a `useX()` wrapping `useQuery({ queryKey: xQueryKey, queryFn: () => xService.list().then(res => res.data), enabled: !!getAccessToken() })`, and (if mutable) a `useXMutations()`/`useUpdateX()` wrapping `useMutation` that calls `queryClient.invalidateQueries({ queryKey: xQueryKey })` or `queryClient.setQueryData(xQueryKey, data)` `onSuccess`. This is what makes e.g. saving a profile field in `AccountPage` instantly update the Header — they share one cache entry. A few older views (e.g. `ProfilePage`, the standalone `/profile` route — not the same as `AccountPage`) still fetch with local `useState`+`useEffect`; don't copy that pattern for anything new, and feel free to migrate a view to the hook pattern if you're already touching it for another reason. Note that server-rendered catalog data (`CategoriesPage`, `ProductsPage`, `CategoryProductsSection`, product-detail `initialProduct`) is a **third**, deliberately separate pattern — see "SSR & the service account" — don't try to route it through TanStack Query, it's fetched once server-side and passed down as props.
- **Toasts live in the mutation hooks, not in the calling component.** `useBasketMutations`/`useUpdateProfile`/etc. call `sonner`'s `toast.success/.error` inside their own `onSuccess`/`onMutate`, so every caller gets consistent messaging for free (e.g. `add` inspects the basket cache in `onMutate` to say "əlavə edildi" vs. "sayı artırıldı" depending on whether the product was already in the basket). Don't add a second toast in the component that calls `.mutate()` — check whether the hook already covers it first.
- **Prefer adjusting state during render over a `useEffect` that only calls a setter**, when the goal is "reset/sync this state when some other value (a prop, `pathname`, query data) changes." The project's ESLint config flags `setState` calls inside a plain effect body (`react-hooks/set-state-in-effect`) even when it's the standard "sync from a query result" case. The fix used throughout (`Header`'s pathname-triggered search reset, `AccountPage`'s `avatarPreview`/`lastSyncedImgUrl` sync when the profile query resolves) is: keep a `[prevX, setPrevX]` state tracking the last-seen value, and an `if (x !== prevX) { setPrevX(x); setY(...) }` **directly in the component body** (not wrapped in `useEffect`) — React explicitly supports calling setters during render for this exact case and re-renders before committing, so it's not the same as writing to state during render generally.
- Reusable **`ConfirmModal`** (`src/shared/components/ui/ConfirmModal.tsx`) guards destructive/significant actions — removing the last unit of a basket item via the trash icon in `BasketSidebarPanel`/`BasketPage`/`ProductDetailContent`, and (newer) logging out via `Header`'s "Çıxış" button. Its backdrop `onClick` calls `e.stopPropagation()` (needed because it may be nested inside a clickable card like `CategoryProductCard`, which would otherwise treat the click as "open product detail" after the modal closes). Deliberately **not** used for the `CategoryProductCard` grid's own +/− stepper — decrementing to 0 there just removes silently with a toast, no confirmation (a later explicit instruction reversed an earlier attempt to add a confirm step there — don't re-add it without asking).
- **`useHasMounted()`** (`src/shared/hooks/useHasMounted.ts`) — `useState(false)` + `useEffect(() => setHasMounted(true), [])`. Required anywhere a component reads `useBasket()`/`useFavorites()`/`useProfile()` (or anything else backed by the visitor's own token) **and** can now be reached via a server-rendered route (`CategoryProductCard`, `ProductDetailContent`, `BasketSidebarPanel`, `Header`). Without this gate, if the TanStack Query cache already has data cached client-side (e.g. `Header` fetched the basket moments earlier this session) while the server always renders as if no data exists (server never has the visitor's token), the client's first hydration-matching render can diverge from what the server sent — a hydration mismatch that makes React discard and re-render a chunk of the tree, which visually manifested as cards/sidebar corruption. The fix is always the same shape: `const hasMounted = useHasMounted(); const quantity = hasMounted ? realValue : 0` (or equivalent) — force the first render to agree with the server's "nothing yet" state, then let the real value appear in a normal post-hydration re-render. Don't skip this when adding a new component to an SSR'd route that reads personalized data.
- **`useIsomorphicLayoutEffect()`** (`src/shared/hooks/useIsomorphicLayoutEffect.ts`) — `useLayoutEffect` on the client, falls back to `useEffect` on the server (avoids the SSR console warning). Used in `RequireAuth`/`RedirectIfAuth` **only** for the redirect-away check (`if (!getAccessToken()) router.replace('/login')`) — this runs synchronously before paint, so an unauthenticated visitor never sees a flash of gated content. Revealing children when auth **is** confirmed still uses a plain `useEffect` (a second, separate effect) — deliberately, so a legitimately-authenticated visit still gets the fast, non-blocking "Loader paints immediately, content pops in a beat later" feel instead of the browser sitting frozen while the whole authenticated subtree renders synchronously before it's allowed to paint anything. Don't merge these two effects back into one — that reintroduces the flash-avoidance win but loses perceived responsiveness for the common (authenticated) case.
- **Anonymous visitors and basket/favorite actions**: since `/categories`, `/products`, and their product-detail routes are reachable without login (see "Backend / API"), `useBasketMutations` (`add`/`remove`/`removeAll`/`clear`) and `useToggleFavorite` each check `getAccessToken()` inside their `mutationFn` before doing anything else; if there's no token they call `router.push('/login')` and reject the mutation (`Promise.reject(new Error('AUTH_REQUIRED'))`) instead of letting the request 401 silently. Any new mutation reachable from one of these public routes needs the same guard — copy the `requireAuth()` helper pattern from `useBasket.ts` rather than reinventing it.

## Dev tooling
- `package.json`'s `dev` script runs `next dev --turbopack` (switched from `--webpack`) — Turbopack compiles routes on demand much faster, which matters a lot in this project given how many routes are now genuinely server-rendered per-request (service-account round-trips). If Turbopack ever needs to be reverted for a compatibility reason, it's a one-word swap back to `--webpack`; confirm with the user first, this was a deliberate perf choice.
- Three ESLint errors (`react-hooks/set-state-in-effect`) are **permanent, expected, and not fixable within this lint rule**: `RequireAuth.tsx`/`RedirectIfAuth.tsx` (the plain `useEffect` that reveals children after an auth check — see "Data fetching & mutations") and `useHasMounted.ts` (`setHasMounted(true)` on mount). All three are the standard React "detect that we're now mounted/confirmed" idiom with no reactive prop/value to render-time-diff against, so the render-time-adjustment workaround used elsewhere in the codebase doesn't apply. Don't spend time trying to "fix" these three specifically — a clean `eslint .` run should show exactly these three and nothing else.
