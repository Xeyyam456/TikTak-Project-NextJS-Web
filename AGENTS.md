# TIK TAK — project structure & conventions

## Folder layout
- `src/app` — routing only. Each `page.tsx` is a thin wrapper: imports a view from `@/views`, adds `metadata`/`generateMetadata`, and wraps with `RequireAuth`/`RedirectIfAuth` if needed. No business logic here.
- `src/views` — the real per-route UI + data fetching (client components, `useEffect`/`useState` fetch pattern). One file per route, barrel-exported via `src/views/index.ts`.
- `src/shared/components` — reusable UI (`ui/`, `layout/`, `landing/`, `auth/`, plus top-level like `ProductCard.tsx`, `CategoryCard.tsx`, `CategoryProductCard.tsx`). Barrel: `src/shared/components/index.ts`.
- `src/shared/hooks` — reusable hooks (e.g. `useCardCarousel`).
- `src/assets` — static assets meant to be ES-imported (not served raw from `/public`): `src/assets/images/` (e.g. `category.png`, `tiktak-login.webp` — the strawberry/milk banner graphic reused across auth + categories), `src/assets/fonts/`, `src/assets/web-icon/`. Import directly (`import x from '@/assets/images/foo.png'`) and render via plain `<img src={x.src}>` — see next section for why not `next/image`.
- `src/services` — one file per API domain (`product.service.ts`, `order.service.ts`, etc.), all going through `src/services/httpClient.ts` (axios wrapper with token refresh interceptor). `src/services/Auth/auth.service.ts` is the one exception living in a subfolder.
- `src/types` — **the only place `interface`/`type`/enum-const declarations may live.** Organized by domain folder (`user/`, `product/`, `campaign/`, `order/`, `basket/`, `category/`, `auth/`, `upload/`, `shared/`, `common/`). One declaration per file, filename === export name (e.g. `types/product/Product.ts`, `types/product/ProductCardProps.ts`). Each domain folder has its own `index.ts` barrel; component `*Props` types live here too (not inline in the component file). Cross-domain imports go through the sibling domain's barrel (`from '../category'`); same-domain imports are direct (`from './OrderStatus'`). Top-level `src/types/index.ts` re-exports everything.

## Backend / API
- Real backend: `https://api.sarkhanrahimli.dev/api/tiktak` (documented in `web.md` at repo root — client/web scope only; there's a separate admin API not covered here).
- Base URL comes from `NEXT_PUBLIC_API_BASE_URL` in `.env.local` (not committed — recreate it if missing: `NEXT_PUBLIC_API_BASE_URL=https://api.sarkhanrahimli.dev/api/tiktak`). Without it, every request silently fails and pages render empty.
- Auth is bearer-token based, tokens stored in `localStorage` (`access_token`/`refresh_token`, managed in `httpClient.ts`). `RequireAuth`/`RedirectIfAuth` (in `src/shared/components/auth/`) check `localStorage` client-side only — they don't validate the token server-side.
- **Most endpoints require auth** (`/products`, `/products/:id`, `/categories`, `/basket`, `/orders/*`, `/profile`) — confirmed via direct testing, not just docs. Only `/campaigns` is public. Any route that calls one of the auth-required endpoints must be wrapped in `RequireAuth` — either directly in `page.tsx` (see `src/app/products/page.tsx`, `basket/page.tsx`) or once in a parent `layout.tsx` covering the whole subtree (see `src/app/categories/layout.tsx`, which wraps both `/categories` and `/categories/[id]`) — or it'll silently show empty data instead of a real error.
- `next.config.ts` `images.remotePatterns` must list every real image host the API returns (currently `picsum.photos`, `uploads.sarkhanrahimli.dev`, `www.tiktak.az`) or `next/image` throws at render time and the whole subtree fails silently. Because category/product image hosts are attacker-uncontrolled but still *unpredictable* (API-driven, not guaranteed to match the allowlist), `CategoryCard` and `CategoryProductCard` deliberately use a plain `<img>` (not `next/image`) for API-provided images — an unlisted host just fails to load the image instead of crashing the page. Prefer this pattern for any new component rendering API-supplied image URLs.
- Some `web.md`-documented query params are marked "(disabled)" — take that literally, not as "optional." E.g. `GET /products?category_id=` returns a 400 on the real backend despite being documented. Filter client-side on `product.category.id` instead of trusting the query param.
- There is a reference admin panel at `https://github.com/Xeyyam456/TikTak-Project-Admin-Panel` (Vite/React) — same backend, useful to cross-check endpoint paths/response shapes and its `src/types` folder structure (which this project's `src/types` convention was modeled after, minus its `*Api`-vs-UI-model split since this app renders the API shape directly).

## Layout / chrome rules
- `SiteChrome.tsx` controls Header/Footer per route: `/login` and `/register` render with **no chrome** at all; **Footer only renders on `/` (landing)** — every other route gets Header but no Footer.
- `SiteChrome.tsx`'s `<main>` has `bg-neutral-50` (not white) for every non-login/register route — this is intentional site-wide now, not a one-off for categories.
- Header shows a centered search input on every route except `/`; on `/` it's just the logo + nav. The address block (`Header.tsx`, next to the logo) fetches the real address via `profileService.get()` (only if an access token exists) and shows `profile.address`, falling back to "Ünvanınızı seçin" if the user has no token or no saved address yet.
- Brand color is `--primary: #114F2E` (green), defined in `globals.css` and used via `text-primary`/`bg-primary`/`border-primary` Tailwind classes — don't hardcode the hex elsewhere, use the token. Note several newer category-page elements use one-off hex greens (`#92D871`, `#0A955E`, `#76CB4F`) that are visually related but distinct tokens, not `--primary` — matched to existing AuthPage/banner colors, not something to "fix" to `--primary`.
- Global scrollbar is hidden everywhere (`globals.css`) but scrolling still works; this was intentional, not a bug.
- Fonts (`src/app/layout.tsx`): `Roboto` (site-wide default, via `--font-roboto` → `--font-sans`) **must** load with `subsets: ["latin", "latin-ext"]`, not just `["latin"]` — Azerbaijani letters (ə, ş, ç, ğ, ö, ü) live in `latin-ext` and silently fall back to a different system font otherwise. `Poppins` (`--font-poppins`) is also loaded, used only for display text inside the green promo banners (via inline `style={{ fontFamily: 'var(--font-poppins)' }}`) as a free stand-in for the (unlicensed, can't be downloaded) "Codec Pro" font from the original design mockups.

## Categories feature (`/categories`, `/categories/[id]`)
- `/categories` (`CategoriesPage`) is the grid overview: a green promo banner (reusing `src/assets/images/tiktak-login.webp`) plus a `CategoryCard` grid, all from `categoryService.list()`.
- `/categories/[id]` is a product listing for one category. It's split across a **persistent layout + swappable page** on purpose:
  - `src/app/categories/layout.tsx` + `src/views/CategoryDetailLayout.tsx` — wraps `RequireAuth`, fetches the categories list once, and renders the left sidebar (category list + `category.png` promo banner) and the right "Səbətim" (basket) panel. Branches on `usePathname() === '/categories'` to render bare `{children}` (no shell) for the index route.
  - `src/app/categories/[id]/page.tsx` + `src/views/CategoryProductsSection.tsx` — just the middle product grid, fetches `productService.list()` filtered client-side by `product.category.id`.
  - **Critical gotcha:** the shared layout must live at `src/app/categories/layout.tsx`, **not** `src/app/categories/[id]/layout.tsx`. A layout placed inside the `[id]` folder still gets remounted by Next.js every time the `id` param changes (verified empirically with Playwright — DOM identity lost, effects re-ran), defeating the point of a persistent shell. Read the dynamic id client-side via `useParams()` in the persistent component instead of via server `params`.
  - Sidebar height is measured via `ResizeObserver` in `CategoryDetailLayout` and shared to `CategoryProductsSection` (and the basket panel) through a small React Context (`useCategorySidebarHeight`, exported from `CategoryDetailLayout.tsx`) so the "no products" empty state, the loading state, and the product grid can all match the sidebar's height. The product grid uses `content-between` + that same fixed height so multiple rows spread out to end flush with the sidebar's bottom edge.
  - `CategoryProductCard` (used only on the detail page's product grid, not `ProductCard`) renders a real image, price, and an "Səbətə əlavə et" button that swaps to a `− <qty> +` stepper on click (optimistic UI — state updates immediately, `basketService.add/remove` fires in the background, rolls back only on error). Reverts to the plain button at quantity 0.

## Known intentional gaps (don't "fix" without asking)
- "Bizim göstəricilər" stats on the homepage (`StatsSection.tsx`) are hardcoded — there's no stats endpoint in `web.md` yet (`stats.service.ts` is an empty TODO placeholder).
- `/account`, `/favorites` pages are intentionally empty placeholders (heading only) — interior design/data-fetching hasn't been requested yet. (`/categories` is now fully implemented — see above.)
- `ProductCard` (the generic one used by `ProductsPage`) still renders a blank placeholder square instead of the real product image — not yet wired up. `CategoryProductCard` (categories detail page) is a separate, already-real-image component — don't confuse the two.
